Agents & Operations

Agents that complete tasks instead of answering questions — and the supervision, evidence, and boundaries that make agent work safe to run.

Agents doing real work

An agent is a model given tools, a goal, and room to act across several steps. The difference between a chatbot and an agent is the difference between answering a question and completing a task. Real work shows the difference clearly. At the Allen Telescope Array, agents now steer the search from a single plain-language request, planning observations and working the stream as data arrives; a pulsar surfaced live during that work. Nothing about that result came from a bigger prompt. The result came from an arrangement: a clear goal, instruments exposed as tools, and a workflow sturdy enough for the agent to move inside. The pattern repeats everywhere agents succeed. The model supplies judgment at the decision points; the surrounding system supplies reach, memory, and discipline.

Freedom at the decision, structure at the execution

The strongest operating pattern separates choosing from doing. Cloud platforms now let existing, tested workflows be handed to agents as tools: the agent decides which workflow fits the situation, and the workflow then executes with the rigidity of ordinary software. Freedom at the decision, rigidity at the execution. The reverse arrangement, freedom during execution, is where agents wander, improvise against production systems, and create the incidents that fill post-mortems. Teams designing agent systems should ask of every step: does this step need judgment, or does this step need reliability? Judgment goes to the model. Reliability goes to the workflow. Mixing the two up is the most common design error in the field, and the easiest to avoid once seen clearly.

Trust is bought with supervision

The market has already voted on autonomy. Across 3,222 enterprise reviews analysed by G2, 77 percent of buyers trust their agent, only 7 percent would grant total autonomy, and 79 percent ask for visibility and control first. Read plainly: trust exists, autonomy does not, and supervision is the feature that closes the gap. Buyers are not afraid of agents; buyers are refusing black boxes. An agent that shows the evidence behind a recommendation, names the tools used, and stops at the boundaries set for the agent will be used daily. An agent that acts silently and explains later will be switched off, however capable the underlying model may be. Supervision is not a brake on the technology. Supervision is the product.

The first hour of an outage

Operations work shows what supervised agency looks like under pressure. When a service fails, the first hour is mostly a search problem: telemetry, logs, and recent changes must be gathered, compared, and turned into a short list of plausible causes. AI SRE agents now do that searching at machine speed, presenting evidence rather than verdicts, while production approval stays with the engineers. The division of labour is exact. The agent searches everything, instantly, and shows the receipts. The human decides what happens to production. Any team evaluating agents for operations should demand the same split: search can be delegated, evidence must be shown, and the final action remains a human decision with a name attached.

Operating principles we keep

Four principles run through every deployment our studio touches. First, scope the goal in plain language and keep the scope narrow enough to verify. Second, expose tools deliberately; an agent should reach exactly the systems the task requires and nothing beyond. Third, log everything an agent does in a form a person can replay the next morning. Fourth, set the autonomy boundary before the first run, not after the first surprise: which actions happen automatically, which need approval, and which never happen at all. Agents are not magic, and agents are not a menace. Agents are a new kind of worker inside the system, and the quality of the work follows the quality of the arrangement around them. The guides on context engineering and on data explain the two arrangements that matter most: what the agent gets to see, and whether what the agent sees can be believed.

Signs a deployment is ready

Readiness for agent work has visible signs. The goal fits in one plain sentence that a new team member could repeat. The tool list is short enough to print, and every tool on the list earns a place by serving the goal. The logs from a trial run read like a story a person can follow, with decisions and evidence visible at each step. The approval boundary is written down where the operator can find the boundary at 2 a.m., not buried in a design document. And a rehearsal has already produced one boring failure, found in practice rather than in production. Deployments missing those signs are not behind schedule; the deployments are unfinished designs hoping the model will compensate. Models compensate for many things. Missing boundaries are not among them.
